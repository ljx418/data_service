4. 项目卡片：面向人的理解

data_service
知识治理 / 项目智能中台
PythonMCPHTTPGraph/Wiki

我理解它是 workspace 里的“知识与项目理解基础设施”：其他会议、学习、求职、代码助手类应用可以通过 MCP/CLI/HTTP 调它，而不是直接读内部 workspace。当前本阶段又补了 Agent Productization，使 Codex 类 Agent 能按 playbook 和 portal 快速读项目。

适合人类使用方式：导入项目 → 看 Portal → 让 Agent 读 Playbook → 针对任务生成阅读路径 → 用 closure/audit 判断是否可信。

harnessOS
多功能 AI framework / runtime governance
Deep AgentsLangGraphV4/V6 docsPython

我理解它不是单一工具，而是一个面向多业务能力的 Agent framework：会议、面试、知识库、视频生产是产品能力；V4/V6 文档线显示它在持续建设 headless workflow、controlled runtime、identity/tenant、credential、audit、agent governance、distributed runtime 等控制面能力。

当前能看懂的重点：它非常依赖文档中的“Allowed Claim / Forbidden Claims / Evidence Gate”。因此对 HarnessOS 的正确展示不应只画目录图，而应把 docs 中的目标控制平面和代码中的当前实现事实分开核查。

navia
Chrome 阅读伴航 / headless runtime
ChromePage ReadingTS/JSPython

我理解 Navia 是一个网页阅读助手：页面内浮球打开双轨 AI 面板，读取当前页面、摘要、回答基于页面的问题，并生成可追踪的 Mermaid mindmap。它的 docs/active 结构显示它很适合拆成模块 workpack 给多个 Agent 并行开发。

适合用本项目辅助的点：先生成 active docs 的 authority registry，再让 coding agent 只读自己模块相关文档和 allowed directories，避免跨模块误改。

codexPat
桌面 Agent 状态宠物
macOSTauri?pnpmCodex workflow

我理解 codexPat 是一个把 Codex/Agent 状态变成人类可感知桌面反馈的产品。它的文档非常强调“allowed claim / forbidden claim”，说明项目曾多次避免把局部 smoke 夸大成 MCP ready 或第三方 Agent 完整集成。

适合用本项目辅助的点：做阶段文档 authority 排序，避免历史 V3/V6/V7/V10/V22 文档互相冲突；再把当前 active claim 和实际 package/workspace 能力对齐。

5. 如果继续用本项目深入理解这些项目

第一层：项目画像

生成 profile、taxonomy、authority rules，把项目术语和历史阶段整理清楚。

第二层：人类 Portal

生成项目首页：目标、当前实现、模块地图、风险、推荐阅读路径。

第三层：Agent 开发入口

生成 coding_agent playbook 和 task navigation，让 Agent 先读最小上下文。

第四层：文档代码核查

对 docs claim 和代码事实做 supported / weak / unsupported 分类。

第五层：治理闭环

记录 feedback，生成 rules，approved 后做 read-time overlay，不改写原文档。

第六层：持续验收

每次项目变更后更新 closure matrix，确认哪些理解仍然可信。
